# СНИМОК 5: U-Boot — L1/L2 + МЕНЯЮЩИЙСЯ канал SPL (JTAG) [КЛЮЧЕВОЕ]
> Загрузка с SD + U-Boot, наша прошивка, тест активен. Дата: 2026-10-10.

## MMU / L1-таблица (TTBR0 многоступенчатая)
`
TTBR0 = 0x5FFF4000  (2-уровневая: L1 -> L2 страницы, как у U-Boot)
0x5fff4000: 5fff0003 00000000 5fff1003 00000000 5fff2003 ...  <- page-table (тип 0b11)
0x5fff4020: ffffffff ffffffff ...        <- секции 0x400... по 0xFFFFFFFF (НЕ section!)
`
Вывод:
- U-Boot маппит DRAM через L2-страницы, НЕ через section-записи.
- Для секций 0x40000000+ L1-запись = 0xFFFFFFFF (незаполнена/невалидна как section).
- mmu_mark_uncached() считает такие секции невалидными (тип != 0b10) и НЕ помечает
  их uncached -> LLI/буфер остаются cacheable -> гонки DMA/cache -> "мусор"/тишина.
  В FEL (TTBR0=0x8000) записи section (0x40101DE2, тип 0b10) -> работало.

## Изменение канала SPL (КЛЮЧЕВОЕ)
`
В одной загрузке SPL держит канал 4 (0x01C02200): EN=1 DESC="SPL" CUR="eGON"
В ДРУГОЙ загрузке SPL держит канал 5 (0x01C02240): EN=1 DESC="SPL" CUR="eGON"
`
SPL кладёт свой дескриптор в НЕДЕТЕРМИНИРОВАННЫЙ канал. Значит фиксированного
"свободного" канала НЕ существует — нужно после старта гасить ЗАНЯТЫЙ канал
(тот, где DESC/EN не наш) или гарантированно переинициализировать выбранный.

## Что проверить/сделать дальше
1. Исправить mmu_mark_uncached() для работы с 2-уровневой таблицей U-Boot, либо
   самому построить section-записи для своих .coherent/.dma_buf в L1 (перезаписать
   нужные idx на section-запись с uncached-атрибутом).
2. dma_pick_channel() должен не просто брать свободный по EN/busy, а гарантировать,
   что выбранный канал не перезапишется SPL (проверять DESC после старта).

# СНИМОК 6: U-Boot L2-таблица — как маппится наш LLI/буфер (JTAG) [КЛЮЧЕВОЕ]
> Загрузка с SD + U-Boot. Чтение L1+L2 через JTAG. Дата: 2026-10-10.

## Расшифровка L1 (ожидаемая для L2) и L2
- L1 (0x5fff4000): записи type page-table (0x5fff1003 и т.д.) на 0x5fff1000/2000/3000.
  Секции 0x40000000+ -> L1 = 0xFFFFFFFF (не section!).
- L2 #1 (0x5fff1000), large pages 16KB, для DRAM:
  `
  0x5fff1000: 40000449 00000000   <- base 0x40000000  attr 0x449 (cacheable)
  0x5fff1008: 40200449 00000000   <- base 0x40200000  (наш .dma_buf!) cacheable
  0x5fff1010: 40400449            <- 0x40400000
  ...
  `
- Атрибут 0x449: B/C биты присутствуют -> write-back cacheable.
- L2 #2/#3 (0x5fff2000/3000): записи 0x80000441/0xc0000441 + 0x00400000 (высокие
  адреса) — периферия / прочие.

## ВЫВОД (критично!)
- В U-Boot наш .coherent (0x40100000) и .dma_buf (0x40200000) мапятся
  **L2-large-page (16KB, attr cacheable 0x449)**, а НЕ секциями.
- mmu_mark_uncached() работает только с section-записями (L1 type 0b10).
  Для L2-страниц он бесполезен -> наш LLI/буфер остаются cacheable
  -> DMA/cache гонки -> мусор/тишина в SD-режиме.
- Чтобы пометить uncached в U-Boot, нужно править L2-записи нужных 16KB-страниц
  (сбросить B/C биты в 0x449 -> 0x401), либо иначе решить когерентность.
- В FEL (TTBR0=0x8000) DRAM = section (0x40101DE2, тип 0b10), там mmu_mark_uncached
  работает -> звук идёт.

# СНИМОК 7: U-Boot — канал SPL недетерминирован и АКТИВЕН (JTAG) [РЕШАЮЩЕЕ]

# СНИМОК 8: JTAG-зонд — записи в канал РАБОТАЮТ (нет защиты на запись) [РАЗГАДКА]
> Загрузка SD+U-Boot, тест остановлен. Дата: 2026-10-10.

## Результаты прямого JTAG-зонда
- L1-записи 0x5FFF5000 (секции 0x400..0x402) = 0xFFFFFFFF (невалидны как section).
  Но код исполняется -> DRAM маппится через ДРУГУЮ L2-таблицу (не проверенную).
- mww 0x01C02248 (DESC канала 5) = 0x40100000 -> считывается 0x40100000 (ДЕРЖИТ!).
- Значит НЕТ защиты на запись канальных регистров DMA. Через JTAG всё работает.

## РАЗГАДКА
- Через JTAG DESC канала пишется и держится (0x40100000).

# ОШИБКА 2: отключать MMU на лету нельзя (Undefined Instruction)
> Дата: 2026-10-10. PC=0x40000004 (вектор Undefined Instruction).

## Что было
Попробовал mmu_disable() в начале kmain: выключил MMU+caches (SCTLR M/C/I=0) на
работающем коде. Результат - CPU ловит Undefined Instruction (PC=0x40000004),
т.к. выключение MMU на лету сбивает конвейер/пред-выборку для кода из DRAM.

## ОШИБКА исправлена
Вернулся к mmu_setup() с ПРАВИЛЬНОЙ разметкой (из анализа):
- DRAM (0x40000000+512МБ) = Normal UNCACHED: (i<<20)|0x00005C02 (TEX=1,C=0,B=0,S=1).
- Периферия/низкие = Device/Strongly-ordered: (i<<20)|0x00000C02.
- Секции 0x600..0xFFF = 0 (Fault).
- DACR = 0x55555555 (все домены Client).
- ПЕРЕД переключением TTBR0: clean всей таблицы из D-cache (шла строки по 32),
  затем mcr c2,c0,0 + DSB + TLBIALL + DSB + ISB.
- .mmu_pt в linker.ld (0x40558000, 16KB, aligned 0x4000), обнуляется в boot.s.
- mmu_mark_uncached теперь NOP (наша таблица уже разрежает DRAM uncached).

## УРОКИ
1. НЕ отключать MMU на лету (код из DRAM сломается).
2. DRAM в своей таблице - Normal UNCACHED (0x5C02), а не cacheable и не
   strongly-ordered (из последнего код не исполняется, из cacheable DMA не видит).
3. Обязательны DACR=0x55555555 и clean таблицы перед переключением TTBR0.
